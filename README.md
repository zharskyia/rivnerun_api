# scrape-config.json

Конфіг правил скрейпінгу сайту [rivnerun.club](https://rivnerun.club/) для застосунків **Rivne Running Club** — Android та iOS. Застосунки не мають доступу до бекенду сайту, тому отримують дані (новини, тренування, забіги, товари, рекорди, партнерів тощо) шляхом розбору HTML публічних сторінок за допомогою регулярних виразів. Цей файл виносить ці регулярні вирази з коду застосунків назовні, щоб їх можна було виправити одразу після зміни верстки сайту — **без випуску нових версій застосунків**.

## Як це працює

Нижче описано Android-застосунок. iOS-версія завантажує й кешує файл так само, але поки не перевіряє регулярні вирази перед використанням (див. «Фолбек-механізм при помилці»).

1. При кожному запуску застосунок намагається завантажити цей файл за URL, зашитим у `SCRAPE_CONFIG_URL` (`ScrapeConfig.kt` у репозиторії [rivnerun.club_android](https://github.com/zharskyia/rivnerun.club_android)) — зараз це raw-посилання на цей файл у гілці `main` цього репозиторію.
2. Якщо файл успішно завантажився, є валідним JSON і всі регулярні вирази пройшли перевірку (див. «Фолбек-механізм при помилці») — застосунок кешує його локально (`SharedPreferences`) і одразу використовує.
3. Якщо мережа недоступна або файл не завантажився — застосунок бере **останню успішно закешовану версію**.
4. Якщо кешу ще немає (перший запуск без мережі) — застосунок використовує вбудовані в код Kotlin значення за замовчуванням (параметри класу `ScrapeConfig` у `ScrapeConfig.kt`), ідентичні вмісту цього файлу на момент останньої синхронізації.

Тобто зміни тут впливають на застосунки **одразу після наступного запуску з інтернетом**, без оновлення в Google Play чи App Store.

## Формат файлу

Кожне поле — рядок з регулярним виразом у синтаксисі Java/Kotlin `Regex` (iOS використовує `NSRegularExpression`, у якого для звичайних конструкцій той самий синтаксис). У JSON зворотний слеш (`\`) і лапки (`"`) всередині значення екранується подвійним зворотним слешем/бекслешем (`\\`, `\"`) — це стандартне екранування JSON, не специфіка проєкту.

Більшість патернів починаються з `(?is)` — це inline-прапорці: `i` (регістронезалежний пошук), `s` (крапка `.` матчить і символ нового рядка). Їх не варто прибирати, інакше матчинг багаторядкового HTML зламається.

### `version`
Номер версії конфіга (зараз `1`), ціле число. Інформаційне поле, застосунки його не перевіряють.

### `home`
Патерни для головної сторінки (`/`).

| Поле | Призначення |
|---|---|
| `descriptionMeta` | Витягує вміст `<meta name="description" content="...">` для короткого опису на екрані "Головна". |

### `article`
Спільні патерни для всіх "текстових" сторінок (`/club`, `/istoriya`, `/zasnovniki`, `/partneri`, `/contacts`, `/donate`, `/rekordi-klubu`) і сторінок окремих новин.

| Поле | Призначення |
|---|---|
| `articleTag` | Знаходить вміст тега `<article>...</article>`. |
| `bodyDivMarker` | Усередині статті знаходить відкриваючий тег `<div itemprop="articleBody">`; застосунок далі сам рахує вкладеність `<div>`, щоб коректно вирізати весь блок до відповідного закриваючого тега. |
| `image` | Фото всередині тіла статті (`<img src="...">`, разом із галереєю) — для сторінки новини в Android-застосунку. Поле необов’язкове: якщо його немає, застосунок використовує вбудований патерн. iOS-версія його поки не читає. |

### `news`
Патерни для архіву новин (`/news`).

| Поле | Призначення |
|---|---|
| `articleLink` | Знаходить посилання `<a href="/...">...</a>`, що веде на окрему новину. |
| `image` | Картинка новини (очікується шлях виду `/img/500/...`). |
| `title` | Заголовок новини всередині `<strong>`. |
| `date` | Дата у форматі `ДД.ММ.РРРР` всередині `<span>`. |

### `training`
Патерни для розкладу тренувань (`/training`, а також блок розкладу на сторінці `/rekordi-klubu`).

| Поле | Призначення |
|---|---|
| `table` | Таблиця з класом `training-schedule__info`. |
| `row` / `cell` | Рядок (`<tr>`) і клітинка (`<td>`) таблиці. |
| `firstParagraph` | Перший `<p>` у клітинці з днем/датою/часом. |
| `date` / `time` | Дата (у `<strong>`) і час (у `<span>`) всередині `firstParagraph`. |
| `removeStrong` / `removeSpan` | Використовуються, щоб прибрати дату/час з тексту й лишити лише назву дня. |
| `paragraph` | Параграфи в другій клітинці (назва тренування, локація). |

### `races`
Патерни для списку забігів (`/events`).

| Поле | Призначення |
|---|---|
| `listDivMarker` | Контейнер `<div class="...race-list...">`. |
| `link` | Посилання на окремий забіг усередині списку. |
| `titleStrong` / `titleHeading` | Назва забігу — спершу шукається в `<strong>`, якщо немає — у заголовку `<h1>`–`<h6>`. |
| `date` | Дата всередині `<time>` або `<span>`. |

### `products`
Патерни для каталогу товарів (`/shop`).

| Поле | Призначення |
|---|---|
| `link` | Посилання на товар (очікується шлях `/tovar/...`). |
| `image` | Картинка товару. |
| `title` | Назва товару в `<strong>`. |
| `price` | Ціна в `<span>`. |

### `records`
Патерни для сторінки "Рекорди клубу" (`/rekordi-klubu`) — єдина сторінка з вкладками.

| Поле | Призначення |
|---|---|
| `tabsList` | Контейнер `<ul class="tabs__list">` з назвами вкладок. |
| `tabTitle` | Назва окремої вкладки (`<span>` усередині `tabsList`). |
| `tabsContentMarker` | Контейнер `<div class="tabs__content">`, що містить по одному `<div>` на кожну вкладку (в тому ж порядку, що й `tabsList`). |
| `paragraph` | Параграфи всередині вкладки. **Логіка групування:** перший непорожній `<p>` після порожнього `<p><br></p>` (або перший параграф вкладки) вважається заголовком групи (напр. "ЧОЛОВІКИ" або ім'я спортсмена); наступні непорожні параграфи до наступного роздільника — записи цієї групи. Ця логіка в коді застосунку, не в конфізі — якщо сайт змінить структуру розбиття на групи, саме регулярку `paragraph` відредагувати не вийде, доведеться міняти код. |

### `partners`
Патерни для логотипів партнерів на сторінці `/partneri`.

| Поле | Призначення |
|---|---|
| `listDivMarker` | Контейнер `<div class="...partners__list...">`. |
| `link` | `<a href="...">` з посиланням на сайт партнера, що обгортає логотип. |
| `image` | Картинка логотипу всередині `link`. |

## Фолбек-механізм при помилці

Android-застосунок при декодуванні JSON робить окремий fallback для кожного поля: якщо секція (`home`, `news`, `records`...) або конкретне поле відсутнє в файлі чи має значення `null` — береться значення з вбудованого дефолту, а не весь конфіг цілком. Невідомі поля й секції ігноруються.

iOS-версія робить fallback для секції цілком: якщо в секції бракує хоч одного поля або воно не рядок, уся секція береться з вбудованих значень, і решта правок у ній на iOS не діє. Тому у файлі завжди мають бути **всі секції й поля** — це контролює автоматична перевірка (див. нижче). Редагувати при цьому можна лише ті поля, які реально зламались.

Перед використанням і кешуванням Android-застосунок перевіряє кожен патерн: він має компілюватися як регулярний вираз і містити щонайменше стільки груп захоплення, скільки з нього читає код. Дві групи потрібні для `news.articleLink`, `races.link`, `products.link` і `partners.link`. Жодної — для маркерів (`bodyDivMarker`, `listDivMarker`, `tabsContentMarker`), `removeStrong` і `removeSpan`. Для решти полів потрібна одна група. Якщо хоч один патерн не проходить перевірку, **весь віддалений конфіг відхиляється й не кешується**, а застосунок продовжує працювати на останньому робочому конфігу з кешу (або на вбудованих значеннях). Причину видно в Logcat з тегом `ScrapeConfig`.

Якщо конфіг пройшов перевірку, але розібрати окрему сторінку все одно не вдалося (змінилась верстка, патерн нічого не знаходить тощо), цей розділ залишається з востаннє збереженими даними, а застосунок показує повідомлення про неповне оновлення. Деталі — у Logcat з тегом `ClubSiteRepository`.

iOS-версія поки не перевіряє конфіг цілком: некоректний патерн там не зупиняє застосунок, але розділ, який від нього залежить, не оновиться коректно.

## Автоматична перевірка

Кожен пуш і pull request, що змінює `scrape-config.json`, запускає на GitHub перевірку (GitHub Actions, `.github/workflows/validate-scrape-config.yml`). Скрипт `.github/scripts/ValidateScrapeConfig.java` перевіряє, що:

- файл — строгий JSON у кодуванні UTF-8: без BOM, коментарів, зайвих чи пропущених ком і повторених ключів;
- є поле `version` (ціле число), усі секції й усі поля, і немає невідомих: найчастіше це одруківка в назві, а таке поле застосунки мовчки ігнорують;
- кожне значення — непорожній рядок, який компілюється як регулярний вираз і має потрібну кількість груп захоплення (ті самі правила, що й в Android-застосунку);
- у патерні немає символу backspace: він з’являється, якщо в JSON написати `\b` замість `\\b`.

Результат видно на вкладці **Actions** і біля коміту (✓ або ✗). Кожна помилка вказує рядок і стовпчик у файлі, а в pull request її видно й біля відповідного рядка на вкладці **Files changed**. Лист про невдалу перевірку вмикається в **Settings → Notifications → Actions** вашого профілю GitHub.

Перевірка запускається вже після пушу: зміна в `main` одразу стає доступною застосункам, навіть якщо перевірка потім не пройде. Щоб перевірити зміну до публікації, у веб-редакторі GitHub замість коміту в `main` виберіть **Create a new branch for this commit and start a pull request** і злийте pull request, коли перевірка пройде.

Перевірку можна запустити й локально, з кореня репозиторію (потрібна Java 17 або новіша; якщо `java -version` показує старішу, вкажіть повний шлях до `java` з JDK 17):

```powershell
java "-Dfile.encoding=UTF-8" .github/scripts/ValidateScrapeConfig.java scrape-config.json
```

Список полів і кількість груп захоплення в скрипті мають збігатися з `ScrapeConfig.validationError()` у `ScrapeConfig.kt` Android-застосунку: додаючи чи змінюючи поле в застосунках, оновіть і скрипт.

## Як редагувати безпечно

1. Відкрийте реальну сторінку сайту (`view-source:https://rivnerun.club/...`) і знайдіть фрагмент HTML, який змінився.
2. Складіть/перевірте регулярний вираз (зручно — у будь-якому онлайн-тестері regex з прапорцями `i` та `s`).
3. Екрануйте `\` → `\\` і `"` → `\"` при вставці рядка в JSON.
4. Перевірте, що JSON у цілому валідний: помилка парсингу всього файлу відкидає **весь** конфіг, і застосунок відкочується на кеш/дефолти. Те саме на Android станеться, якщо хоч одна регулярка не компілюється або має замало груп захоплення. Усе це перевіряє скрипт з розділу «Автоматична перевірка» — його можна запустити ще до пушу.
5. Закомітьте й запуште в гілку `main` цього репозиторію (або злийте pull request) — зміна набуде чинності для користувачів автоматично, при наступному запуску застосунку з мережею. Переконайтеся, що біля коміту з’явилася зелена ✓.

## Діагностика на реальному пристрої

Якщо після зміни верстки сайту якийсь розділ застосунку показує старі/кешовані дані або попередження на кшталт "Не вдалося оновити N розділ(и)", підключіть пристрій і подивіться лог:

```powershell
adb logcat -s ClubSiteRepository:W ScrapeConfig:W
```

Там буде видно, яка саме сторінка (`/path`) і з якою помилкою не розібралась, або чому відхилено весь конфіг (`ScrapeConfig`) — це вказує, яке поле конфіга потребує виправлення.

## Пов'язаний репозиторій

Код, що читає й застосовує цей конфіг, живе в репозиторіях застосунків: [rivnerun.club_android](https://github.com/zharskyia/rivnerun.club_android) (`ScrapeConfig.kt` — формат і перевірка, `SiteParsers.kt` — розбір сторінок) і rivnerun.club_iOS (`ScrapeConfig.swift`, `ClubSiteRepository.swift`). Цей репозиторій (`rivnerun_api`) містить лише дані та скрипт їх перевірки — коду застосунків у ньому немає.
